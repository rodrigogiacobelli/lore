## Story

As _a developer whose project was initialised before a configuration key existed_, I want _a later `lore init` to document that key in my `config.toml` header_, so that _I can discover settings without reading Lore's source_.

## Context

FR-36 is a drift problem with a structural fix. `_CONFIG_SKELETON` at `src/lore/init.py:17` is a hand-copied comment block listing two keys; `config.py`'s `_FROM_TOML`, `_EXPECTED_TYPE`, `_ALLOWED_VALUES` and `DEFAULT_CONFIG` are the real registry. The block is seeded once and skipped forever after, so a project initialised at any earlier version never learns about a key added later — and the two copies drift the moment a key is added in one place and not the other.

Tech Spec §9.3 generates the block instead: `config.render_known_keys_header() -> str` builds it from the loader's own tables plus a new `_KEY_DOC` one-line description table. Adding a setting stays a one-field, one-row-per-table edit, and no header text is hand-copied (`standards-dry`).

On an **absent** `.lore/config.toml`, `lore init` writes header plus every key at its default — unchanged from today. On a **present** file, it replaces **only the leading contiguous run of `#` lines**, from the first line to the first line that is not a comment. Every non-comment line is left byte-identical, so values, ordering, blank lines and inline comments all survive.

This bends ADR-013's "seed in place, skip if present" rule for the comment block only. The generated block's first line says so, which makes the social contract match the `<!-- lore:begin -->` marker blocks: inside is Lore's, outside is yours. The ADR amendment recording the exception is owned by the phase-5 codex-apply mission.

## Acceptance Criteria

### E2E Scenarios

#### Scenario 1: A pre-existing config gains the new keys in its header and loses nothing else

**Given** a `.lore/config.toml` written before the `init-*` keys existed, carrying the old two-key header, `show-glossary-on-codex-commands = false`, a blank line, an inline comment on the retention line, and an unknown root key `my-team-setting = 3`
**When** the caller runs `lore init --yes`
**Then** the leading comment block is replaced with one naming all six known keys, and every line from the first non-comment line onward is byte-identical to before the run — including the blank line, the inline comment, and `my-team-setting`

#### Scenario 2: An absent config gets header plus defaults

**Given** a project with no `.lore/config.toml`
**When** the caller runs `lore init --yes`
**Then** the file is created carrying the generated header followed by every known key at its default value, and `load_config` on it returns `DEFAULT_CONFIG`'s field values

#### Scenario 3: The header names every key the loader knows

**Given** any generated header
**When** a test compares it against `config._FROM_TOML`
**Then** every key in `_FROM_TOML` appears in the header exactly once with its type, its default, and a one-line description, and no key absent from `_FROM_TOML` appears

#### Scenario 4: Regeneration is idempotent

**Given** a project already carrying a generated header
**When** the caller runs `lore init --yes` twice
**Then** `.lore/config.toml` is byte-identical after both runs

#### Scenario 5: A file with no leading comments gains one without losing a line

**Given** a `.lore/config.toml` whose first line is `show-glossary-on-codex-commands = true`, with no comment header at all
**When** the caller runs `lore init --yes`
**Then** the generated header is prepended and every original line survives in order, byte-identical

### Unit Test Scenarios

- [ ] `lore.config.render_known_keys_header`: names every key in `_FROM_TOML`, each with its `_EXPECTED_TYPE`, its `_ALLOWED_VALUES` set where one exists, its `DEFAULT_CONFIG` value, and its `_KEY_DOC` line
- [ ] `lore.config.render_known_keys_header`: every line begins with `#`; the block's first line states that it is regenerated by `lore init`
- [ ] `lore.config.render_known_keys_header`: a list-typed key renders as `list of "a" | "b" | "c", default [...]`
- [ ] `lore.config._KEY_DOC`: has an entry for every key in `_FROM_TOML` and no extras — the test that keeps the three tables from drifting
- [ ] `lore.init._replace_leading_comment_block`: replaces the leading contiguous `#` run and nothing else; text from the first non-comment line onward is byte-identical
- [ ] `lore.init._replace_leading_comment_block`: a file starting with a non-comment line gains the header prepended, with no line lost
- [ ] `lore.init._replace_leading_comment_block`: a comment appearing **after** a setting line is not touched
- [ ] `lore.init._replace_leading_comment_block`: an empty file yields header only
- [ ] `lore.init`: `_CONFIG_SKELETON` at `src/lore/init.py:17` no longer exists as a hand-written constant — the header comes from `config.render_known_keys_header()`

## Tech Notes

### Implementation Approach

- **Files to modify:**
  - `src/lore/config.py` — add `_KEY_DOC: dict[str, str]` and `render_known_keys_header() -> str`, built from `_FROM_TOML` (`src/lore/config.py:45`), `_EXPECTED_TYPE` (`:53`), `_ALLOWED_VALUES` (`:60`), `DEFAULT_CONFIG` (`:92`) and `_KEY_DOC`.
  - `src/lore/init.py` — delete `_CONFIG_SKELETON` at `src/lore/init.py:17-27`; `_seed_glossary` at `src/lore/init.py:64` currently passes it to `_seed_skeleton_if_absent` for `config.toml` at `src/lore/init.py:76-81`. Replace that call with a header-aware write: absent file → header plus every key at its default; present file → `_replace_leading_comment_block(path, header)`.
- **Files to create:** none.
- **Schema changes:** none.
- **Dependencies:** US-013 (the four new keys must be in the registry for the header to name them), US-015 (`apply_init` owns the write sequence this call sits in).

The exact rendered shape is Tech Spec §9.3's worked example — a two-line preamble, a blank comment line, `# Known keys (additional keys are accepted, preserved, and ignored):`, then one indented row per key with its continuation lines. The test asserts *structure and coverage*, not the literal block, so a future key does not break it.

Note that `.lore/config.toml` is a **project** file, not seeded content under `src/lore/defaults/`, so ADR-006's no-seed-content rule does not apply and asserting the header's shape is legitimate.
